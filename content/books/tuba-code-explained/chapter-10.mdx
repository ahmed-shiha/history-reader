## الصورة الكاملة أولاً

هذا الملف يصف **طبقة التحكم** — المجموعة من السكريبتات التي تقع بين المهندس وبين النظام الحي. النظام نفسه (Docker image، prompt، ECS service) لا يُعدَّل مباشرةً بالكليك أو بالتعديل اليدوي — كل تغيير يمر عبر هذه السكريبتات.

لو سألتَ: لماذا هذا التعقيد بدل أن أفتح الملف وأعدّله يدوياً؟

الجواب في طبيعة الـ deployment pipeline: Studio في Lightning ← Docker image ← ECR ← ECS task definition ← service revision. **كل خطوة منفصلة، وكل خطوة يمكن أن تُكسر الخطوة التي بعدها بصمت.** السكريبتات تفرض الترتيب وتمنع أن تنسى خطوة.

## القسم الأول: `studio_io.py` — طبقة الاتصال بـ Lightning Studio

### القرار الأهم: لماذا base64 للقراءة والكتابة؟

النظام يعمل على Windows (كما يظهر من `cp1252` وذكر "Windows console"). عند نقل نص عبر SSH بين Windows و Linux، الـ line endings تُسبّب كوارث صامتة:
- `\r\n` (Windows) يتحوّل أحياناً إلى `\r\n` أو `\n` أو `\r` حسب الـ terminal
- Python file على Linux بداخله `\r` سيُفشل `py_compile` بخطأ غامض لا علاقة له بالمحتوى الفعلي

`base64 -w0` يحوّل أي bytes إلى ASCII نقي بدون أي special characters. عند الإرسال: النص → base64 → SSH → `base64 -d > file`. الملف يصل على Linux بالضبط كما أُرسِل بدون أي تعديل. هذا ليس over-engineering — هذا الحل الوحيد الموثوق لنقل code بين أنظمة مختلفة.

### لماذا استُبدل `upload_file()` بالـ `write()` اليدوي؟

الملاحظة في الجدول: "Replaces `upload_file()`, which silently fails". هذا هو أخطر نوع من الأخطاء في أي نظام — الخطأ الذي لا يُعلنعن نفسه. `upload_file()` كانت تنتهي بنجاح ظاهري بينما الملف على الـ studio لم يتغير. كل تغيير بعدها كان يُبنى على أساس زائف. `write()` يُرجع الـ size والـ sha256، فيمكن التحقق فوراً.

### `sprint(s)` — تفصيلة صغيرة تكشف ثقافة البناء

أن يُخصَّص دالة لطباعة نص على Windows console دون crash يعني أن المشكلة حدثت فعلاً وسببت مشكلة حقيقية. `→` و`—` موجودان في النصوص الطبية والـ logs، و`cp1252` لا يحتوي عليهما. بدون هذا الحل، كل stack trace مع هذه الرموز يُفشل السكريبت بـ `UnicodeEncodeError` قبل أن يطبع شيئاً مفيداً.

## القسم الثاني: سكريبتات تعديل الـ Prompts

### القرار الجوهري: `assert n == 1`

```python
n = t.count(old)
assert n == 1, f'﴿label﴾: expected 1 match, found ﴿n﴾'
```

هذا السطر يحمي من خطأ لا يُرى حتى وقت التشغيل: لو وُجدت العبارة القديمة في مكانين في الـ prompt، `replace()` بدون هذا الـ assert ستغيّر الاثنين معاً. النتيجة؟ prompt تم تعديله في مكانين بدل واحد، والتغيير الثاني ربما يُفسد سياقاً آخر تماماً. وبما أن الـ prompt طويل جداً، لن يلاحظ أحد.

الـ assert يجعل السكريبت يتوقف بدل أن يُنتج تغييراً خاطئاً بصمت. هذا اختيار مقصود: **الفشل الصريح أفضل من النجاح الزائف.**

### الفحص بعد التعديل: `assert g in t`

بعد كل التعديلات، يتحقق السكريبت أن العبارات الجديدة فعلاً موجودة في النص. لماذا؟ لأن السكريبت يُضيف عبارات من خلال replace، وإذا كان الـ replace الأول غيّر شيئاً أثّر على سياق الـ replace الثاني، ممكن أن ينتهي بنص يبدو صحيحاً بدون العبارات الجديدة.

### لماذا يُكتب ملف نسخة جديدة ولا يُعدَّل الملف الأصلي؟

`make_v208.py` ينتج `version_20_8_small` من `version_20_6`. لا يُعدّل `version_20_6`. هذا يعني:
1. يمكن رؤية الفرق بين النسختين بوضوح
2. إذا كُسر شيء في `20_8`، الـ fallback جاهز — النظام يكسر والـ registry لا يزال يشير للنسخة القديمة حتى يتم تسجيل الجديدة

### `register_v208.py` لا يُغيّر `LATEST_VERSION`

هذا قرار أمان. الـ register يضيف النسخة للـ registry كخيار متاح، لكن لا يجعلها الافتراضية. يعني: يمكن استدعاء النسخة الجديدة صراحةً في البنشمارك `﴿'prompt_version': 'version_20_8_small'﴾` بدون أن يتأثر أي طلب حقيقي من المستخدمين. فقط عند الثقة الكاملة يتم تغيير `LATEST_VERSION`.

لو تغيّر `LATEST_VERSION` مع كل تسجيل، كل خطأ في نسخة جديدة سيؤثر على كل المرضى فوراً.

## القسم الثالث: Build و Deploy

### Pipeline البناء: الترتيب يهم أكثر من الكود

الـ pipeline هو: كتابة النسخة في `VERSION` على الـ studio ← بناء Docker image ← push إلى ECR ← تسجيل task definition جديدة ← تحديث الـ service.

أي خطوة تُتخطى، النظام يستمر في التشغيل بالنسخة القديمة بصمت تام. هذا ما يُسمى في الملف "the dead-file pattern": الكود الجديد موجود على الـ studio، لكن الـ image لم يُبنى من جديد، فـ ECS لا يزال يخدم النسخة القديمة. لا خطأ، لا تحذير، فقط صمت.

### Credentials: لماذا تمر عبر environment variables بدل config file؟

`build_185.py` يقرأ credentials من `aws_creds` ويمررها كـ environment variables للـ studio shell. ثم: `trap cleanup EXIT` تمسحها. هذا النهج يعني أن الـ credentials لا تُكتب في أي ملف على الـ studio، ولا تظهر في أي log file. تعيش فقط في ذاكرة الـ process وتُمسح عند الانتهاء.

التحذير: `refusing values containing '\''` — هذا لمنع shell injection. لو كانت الـ credentials تحتوي على apostrophe وتم تضمينها في shell command كـ `'$﴿CREDS﴾'`، الـ apostrophe يُغلق الـ string مبكراً وما بعده يُنفَّذ كـ shell command. رفض القيمة أسلم من محاولة escape غلط.

### الـ smoke test بعد كل deploy

السكريبت لا يُعلن النجاح بمجرد انتهاء الـ ECS deployment. يُرسل claim حقيقي، ينتظر النتيجة، ويتحقق:
1. لا escalation code — يعني النظام لم يحيل الطلب لمراجعة بشرية بسبب error
2. عدد العناصر في الرد يطابق عدد العناصر في الطلب

إذا فشل: "Do not start the benchmark". هذا منطقي — البنشمارك يأخذ وقتاً، ونتائجه لا قيمة لها إذا كان النظام غير صحيح.

### ECS Family ≠ Service Name

هذه تفصيلة تُكلف ساعات من الـ debugging إذا غُفل عنها. عند بناء مرجع الـ task definition:

```python
# خطأ: f"﴿service_name﴾:﴿rev﴾"
# صح:  f"﴿family_name﴾:﴿rev﴾"
```

في DEV GPU: service هو `tuba-gpu-inference`، family هو `dev-gpu-inference`. الـ ARN مختلف، والـ ECS يرفض التحديث بدون error واضح أحياناً، أو ينجح لكن يستخدم نسخة خاطئة.

## القسم الرابع: ثغرة التقييم في البنشمارك

هذا القسم هو الأعمق والأقل وضوحاً في الملف. اقرأه بعناية.

### المشكلة الأساسية: ما الذي يقيسه البنشمارك فعلاً؟

البنشمارك يقيس `final_decision` من قاعدة البيانات. هذا يبدو منطقياً — لكن المشكلة أن `final_decision` ليست دائماً قرار النموذج.

النظام يملك عدة "بوابات" (guards) قبل وبعد النموذج:
- Guard قبل النموذج يستطيع رفض الطلب وإحالته لمراجعة بشرية مباشرةً
- Guard بعد النموذج يستطيع تجاوز قرار النموذج وإحالته أيضاً
- Coverage completeness يستطيع تغيير مسار الطلب

في كل هذه الحالات، `decision` المحفوظة ليست `escalated` — بل `pending_review` أو حتى قرار النموذج الأصلي (مثل `approved`). لكن البنشمارك يبحث عن `escalated`.

**النتيجة:** case تستحق escalation، تم إحالتها للمراجعة البشرية بشكل صحيح، لكن عبر guard لا عبر النموذج — تُحسب كـ failure في البنشمارك.

### الجدول الحرج

| مسار الـ escalation | القيمة المحفوظة | البنشمارك يعدّها نجاحاً؟ |
|---|---|---|
| النموذج يقول `escalated` | `escalated` | نعم |
| Guard REJECT | `pending_review` | لا |
| Guard-forced escalation | `pending_review` | لا |
| Coverage completeness | قرار النموذج (مثلاً `approved`) | لا |
| Timeout / JSON error | `pending_review` | لا |

هذا يعني أن النظام قد يكون أذكى مما يبدو في الأرقام: إذا أضافنا guards أقوى تمسك بالحالات الصعبة قبل وصولها للنموذج، سيبدو البنشمارك أسوأ — لأن هذه الحالات ستُحسب كـ failures.

### الأثر الفعلي: صغير لكن مُضلِّل

من الأرقام: في 54 run لكل arm، 6 حالات escalated — كلها CASE-D004 وCASE-D015 عبر `ESC_SAFETY_GUARD`. هذان الـ cases بالذات يُظهران `0 items` في نتائج البنشمارك (الـ `items_ok` column)، وهذا هو الخيط الذي كشف وجود bug في الـ guard: Guard يحيل الطلب قبل إرجاع أي items.

الإصلاح المقترح: بدلاً من البحث فقط عن `decision == 'escalated'`، يجب أيضاً البحث عن `status == 'escalated'` وتسجيل الـ `escalation_code`. هكذا أي guard جديد يُحسب لصالح النظام لا ضده.

### المشكلة الثانية: format البنشمارك vs format الإنتاج

البنشمارك يُرسل:
- CPT codes حقيقية
- ICD codes حقيقية
- أسماء أدوية وجرعات
- كل النص السردي في `clinical_notes`

الإنتاج (Frappe) يُرسل:
- codes داخلية (`CLI-`/`SFDA-`)
- خريطة `__link_titles` لترجمتها
- النص السردي في `supporting_info_structured`
- أحياناً بدون أسماء أدوية أو جرعات

النموذج في البنشمارك يعمل على بيانات مثالية. نفس النموذج في الإنتاج يعمل على بيانات أقل وضوحاً. **درجات البنشمارك تصف نظاماً أحسن تغذيةً مما هو عليه في الواقع.**

هذا لا يعني أن البنشمارك عديم الفائدة — لكنه يعني أن النمط الصحيح هو: بناء نسخة benchmark بـ Frappe format من نفس الـ 25 cases، وقياس الفرق بين النسختين. الفرق هو "تكلفة ضعف البيانات" في الإنتاج.

## القسم الخامس: قواعد التشغيل

`BATCH_SIZE=10` ليس رقماً عشوائياً — 11 يعمل بدون queue، 12 يبدأ في الانتظار. هذا يعني أن الـ GPU يشغّل 10-11 requests بالتوازي بكفاءة مثلى. تجاوز هذا في بيئة الإنتاج يعني requests تنتظر، ومرضى ينتظرون.

`nohup` في الـ launch_detached scripts: الـ benchmark يأخذ وقتاً، ويعمل على `dev-qdrant`. إذا انقطعت الـ session أو انتهت صلاحية الـ AWS credentials على اللابتوب، الـ script يُكمل عمله. النتائج تُكتب إلى `/tmp/bench_all.json` بعد كل جولة — لا تنتظر النهاية.

## الخلاصة الجوهرية

أهم قرار تصميمي في هذا الـ volume هو **فصل طبقات التغيير**: تعديل الـ prompt ≠ بناء الـ image ≠ deploy الـ service. كل طبقة تُسجَّل، تُتحقق، وتُنفَّذ باستقلالية. الثمن: تعقيد. الفائدة: لو كُسر شيء، تعرف بالضبط أين.

والقرار الأكثر صحةً: الإصرار على **الفشل الصريح** (`assert n == 1`، رفض credentials غير صالحة، smoke test قبل benchmark) بدلاً من المضي قدماً بافتراض النجاح. في نظام طبي، النجاح الزائف أخطر بكثير من الفشل المُعلَن.
